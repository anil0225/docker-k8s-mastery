What is a Container, Actually? (Linux Kernel Internals)

A container is not a virtual machine. There is no hypervisor and no guest OS. A container is simply a standard Linux process running directly on the host kernel, restricted by Namespaces (what it can see) and Control Groups (cgroups) (how much it can consume), with root filesystem isolated by OverlayFS.

1. Linux Namespaces: Virtualizing Process Sight

Syscall: clone()

Click each namespace below to inspect how the Linux kernel isolates system resources between the host and the containerized process:

PID Namespace (CLONE_NEWPID) Flag: 0x20000000

Isolates the process ID space. The process inside the container thinks it is PID 1 (init process), allowing it to spawn children, handle signals, and reap zombies. Meanwhile, on the host, the Linux kernel sees it as regular process PID 48209!

Host View: ps aux | grep node -> PID 48209 /usr/bin/node server.js
Container View: ps aux -> PID 1 node server.js
Kernel Syscalls: clone(), unshare(), setns() Kernel: Linux 2.6.24+

2. Cgroups v2 & CFS CPU Bandwidth Throttling

cpu.cfs_quota_us

Linux Completely Fair Scheduler (CFS) enforces CPU limits across fixed time periods (default 100ms / 100,000µs). If a container exhausts its quota before the period ends, the kernel throttles execution, creating mysterious p99 latency spikes!

CFS Period (cpu.cfs_period_us): 100 ms (100,000 µs)
CPU Limit in Manifest (resources.limits.cpu): 1.5 Cores (150,000 µs quota)
Allowed run time in 100ms window: 150 ms total runtime
Multi-thread exhaustion (e.g. 4 worker threads): Quota drained in 37.5 ms!
THROTTLED

For the remaining 62.5ms of the period, the Linux kernel completely suspends all threads of this container. Requests will stall until the next 100ms period begins.

Metric: container_cpu_cfs_throttled_periods_total Fix: Increase quota or avoid hard limits

4. OCI Runtime Stack: Docker to containerd-shim & runc

OCI Spec

Understanding why Docker is not required in Kubernetes (CRI deprecation) and how `containerd-shim` allows daemonless containers that survive engine crashes:

1. User / Orchestrator kubectl / kubelet (or docker CLI)
Sends CRI gRPC / REST
2. containerd (CRI Daemon) Pulls image, unpacks layers into rootfs via snapshotter
/run/containerd.sock
3. containerd-shim (Lightweight Process) One shim per container! Holds stdout/stderr pipes open
Survives containerd restart
4. runc (OCI Low-Level CLI) Calls clone(CLONE_NEW*) syscalls, sets cgroups, executes entrypoint, then exits immediately!
Pure C / Go Binary
Why containerd-shim matters: Because runc exits after fork/exec, the container's parent PID becomes `containerd-shim`. This means containerd can be upgraded or restarted without stopping your running containers!

Container Storage Interface (CSI) Workflow

PV / PVC Binding
Step 1: Dynamic Provisioning

App claims storage with a PersistentVolumeClaim referencing a StorageClass. The external CSI provisioner calls the cloud API (e.g. AWS EBS `CreateVolume`, GCE PD `insert`) and automatically creates a matching PersistentVolume.

Step 2: AttachVolume (Controller Stage)

`attachdetach-controller` instructs the cloud to attach the raw block volume to the specific worker VM instance (e.g. `/dev/xvdf`).

Step 3: NodeStageVolume & NodePublishVolume (Kubelet Stage)

Kubelet invokes the node CSI plugin to format the raw disk with ext4/xfs (NodeStageVolume) into `/var/lib/kubelet/plugins/...`, and then bind-mounts it directly into the container's isolated mount namespace (NodePublishVolume).

Production Architecture & Container Pattern Cookbook

Battle-tested Dockerfiles and Kubernetes patterns designed to eliminate image bloat, security vulnerabilities, and 502/504 errors during rolling deployments.

1. Multi-Stage Distroless Dockerfile (1.2GB → 38MB)

-97% Attack Surface

Compiling in the build stage and copying only the runtime binary into a minimal gcr.io/distroless base eliminates package managers (apt, apk), shell (/bin/sh), and compiler tools from production: 

# STAGE 1: Build & Dependencies (Cached)
FROM golang:1.23-alpine AS builder
WORKDIR /workspace
# Leverage Docker layer cache for dependencies
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o app .

# STAGE 2: Distroless Minimal Production Image
FROM gcr.io/distroless/static-debian12:nonroot
WORKDIR /
COPY --from=builder /workspace/app /app
# Run as non-root UID 65532 for zero-privilege security
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/app"]
Result: 38 MB total size 0 High/Critical CVEs

2. Graceful Shutdown & The SIGTERM Race Condition

Zero Dropped Packets

When a Pod is killed, Kubelet sends SIGTERM simultaneously while the Endpoints controller removes the Pod from Service endpoints. Because iptables takes 1–3 seconds to sync across nodes, incoming requests hit a terminating pod, causing HTTP 502/504 connection refused! 

spec:
  terminationGracePeriodSeconds: 45
  containers:
  - name: web-api
    image: app:v2.1
    lifecycle:
      preStop:
        exec:
          # 1. Delay SIGTERM by 10s to let kube-proxy remove IP from iptables
          command: ["/bin/sh", "-c", "sleep 10"]
    ports:
    - containerPort: 8080
Fix: `preStop` sleep hook + Connection Draining 100% Zero 502 Errors

3. Native Restartable Sidecars (K8s 1.28+)

initContainers.restartPolicy

Historically, sidecars (like Envoy proxies, log forwarders, or Vault agents) raced with the main container. If the proxy started after the app, outgoing traffic failed. With native sidecars, K8s guarantees the sidecar starts before app containers and shuts down after: 

spec:
  initContainers:
  - name: vault-agent-sidecar
    image: hashicorp/vault:1.15
    # Native sidecar definition:
    restartPolicy: Always
    command: ["vault", "agent", "-config=/vault/config.hcl"]
  containers:
  - name: core-application
    image: payment-service:v1.0
Eliminates race condition with proxies K8s GA Feature

4. High-Availability PDB & Topology Spread

Multi-AZ Resiliency

Prevents Kubernetes cluster auto-upgrades or node drains from taking down all replicas simultaneously, while ensuring even distribution across Cloud Availability Zones: 

apiVersion: policy/v1

  minAvailable: 2 # or "66%"
  selector:
    matchLabels:
      app: checkout-api

    matchLabels:
      app: checkout-api
